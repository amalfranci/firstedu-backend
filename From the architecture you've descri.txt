Looking at your pipeline and the review data, the pattern is pretty clear: you have a difficulty-shaping problem and a correctness problem, and they're being caused by two different gaps in the architecture. Neither is fixed by the hard-mandate or self-audit services as they currently stand, because neither of those services actually checks the math.

Root cause 1: Nothing in the pipeline independently verifies the arithmetic

Your hardQuestionMandate.service.js checks structure — step count, concept-cluster count, line count, banned templates. Your difficultySelfAudit.service.js checks how hard it looks via an LLM rubric score. Neither of these touches whether the final numeric answer is actually correct. You mentioned a separate OpenAI verification stage exists, but the review shows 6/10 answer keys wrong — so either:

that stage is checking "is this solution internally consistent" rather than "does this answer match an independent re-derivation," or
it's being skipped/soft-failing for some question types, or
it's also an LLM doing algebra, which fails the same way generation does (LLMs are unreliable at multi-step symbolic arithmetic — errors compound over 4-8 steps, which is exactly your "hard" tier).

Fix: Add a deterministic computational check between skeleton generation and acceptance. For any question with numeric givens (which is most of calculus/coordinate geometry), have code — not an LLM — recompute the final answer from the stated givens using a CAS (SymPy is easiest to wire in, since you're already touching Python-adjacent tooling; a JS equivalent like mathjs/algebrite also works for simpler symbolic cases). Compare that computed value against the skeleton's claimed answer and against the offered options. If they don't match within tolerance, hard-reject before it ever reaches the self-audit stage — no LLM judgment involved. This is the single highest-leverage fix, because right now you're using an LLM to both write the problem and implicitly certify its own arithmetic.

Root cause 2: The hardness gates reward the wrong signal

The reviewer's complaint — "artificially combines unrelated concepts," "not JEE Main style" — is a direct consequence of your gate design. hardQuestionMandate requires ≥2 linked syllabus clusters and ≥4 solve steps for veteran-hard. An LLM under that constraint will often satisfy it the cheapest way possible: bolt two unrelated topics together (e.g., optimization + area) rather than finding a genuinely deep single-concept problem, because concept-fusion is an easy way to hit the "2 clusters" requirement without real depth. Step count is the same story — you can inflate steps without inflating difficulty.

Fix: Ground "hard" in pattern-matching against real JEE archetypes rather than raw concept/step counts. You already have _blueprint objects with pattern/technique/banned-shortcuts — lean harder on curated archetype patterns (drawn from actual past JEE hard questions per chapter) as the primary difficulty signal, and treat concept-cluster count and step count as secondary sanity checks, not the primary gate. Multi-concept fusion should be opt-in per archetype (some real JEE hards genuinely combine area + optimization), not a default way to satisfy a numeric threshold.

Root cause 3: The generation model is likely too weak for this task

gemini-3.1-flash-lite is a small/fast model. Lite-tier models are the ones most prone to exactly the errors you're seeing — sign errors, wrong constant substitution, inconsistent limit conditions (your Q3), area computed on the wrong bound (your Q2/Q6). This isn't really a prompting problem; it's a capability ceiling for multi-step symbolic math.

Fix: For examCalibrated: true / hard-tier generation specifically, route to a stronger model (your commented-out gemini-3.5-flash, or better) even if lite stays default elsewhere for cost. You don't need to swap the whole pipeline — just gate model choice on tier === "hard" || examCalibrated, same condition you already use for the mandate service.

Suggested priority order
CAS-based independent recomputation + hard reject on mismatch — fixes the correctness numbers immediately, is deterministic, and can't be "talked around" by a better prompt.
Upgrade the generation model for hard/exam-calibrated tier.
Rework hardness detection to be archetype-pattern-based rather than step/concept-count-based, so you stop getting Frankenstein concept mashups.
Keep the LLM difficulty self-audit as a tertiary filter after 1–3, not the primary correctness/difficulty gate — it's currently doing a job (verifying math) it's structurally not suited for.
